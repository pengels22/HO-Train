# Controller health and recovery protocol

The existing 12-byte `HC` motor command remains unchanged. Locomotive
telemetry uses a separate versioned `HT` packet whose payload is compact JSON:

```json
{"version":1,"id":1,"state":"ARMED","estop":false,
 "communication_fault":false,"armed":true,"speed":0,
 "sequence":7,"last_command_sequence":12,"session":"boot-1","uptime_ms":100}
```

The dispatcher accepts telemetry only for configured locomotive IDs, tracks
strictly increasing telemetry sequence/session/freshness, and has two distinct
gates. Rearm requires fresh zero-speed telemetry and an exact transaction
acknowledgement. Operating health requires an armed, non-faulted, E-Stop-clear
controller but does not require zero speed, so healthy movement can continue.
Missing or stale required telemetry invokes the same global safety stop path as
a failed required USB controller.

`sequence` is generated by the telemetry publisher and is distinct from
`last_command_sequence`. A fresh random boot session is generated at every
controller startup. Duplicate or out-of-order packets are rejected; a changed
session is treated as a restart and invalidates prior rearm state. The Pi uses
its monotonic receive clock for freshness.

In explicit hardware mode the Pi listens for these `HT` telemetry datagrams on
UDP port `4211`; simulation mode does not bind the telemetry socket.

Registered USB controllers use newline commands. `ESTOP\n` remains an
immediate, acknowledgement-independent stop. Recovery uses `REARM AUTH\n`
and requires a JSON response identifying the controller with `estop=false`,
`motor=false`, `track_power=false`, and no reported fault. `STATUS\n` is the
100 ms heartbeat; a heartbeat cannot clear a latch or authorize motion.

Rearm uses a separate versioned `HR` JSON datagram with broadcast ID 255. The
locomotive must echo
the exact transaction in fresh `HT` telemetry with its current session, armed,
fault-free, E-Stop-clear, zero-speed state. The 12-byte `HC` frame remains
unchanged and is never repurposed for this transaction identity.

The Pi keeps retired boot-session IDs and rejects delayed packets from them.
A changed session is accepted only as a restart event, which latches a
controller fault and requires explicit operator reconciliation followed by a
fresh rearm. Because unauthenticated UDP cannot prove that a changed session
is genuine, production commissioning should pair this with controlled device
registration; a session change is never treated as automatically healthy.

Turntable and tipper state-changing USB commands use bounded newline-delimited
JSON with transaction IDs. The dedicated XIAO accessory parser accepts complete messages up to 191 bytes,
rejects malformed, oversized, missing-authorization, duplicate, and stale
transactions, while plain `ESTOP\n` remains available immediately.

Simulation creates an empty logical registry only. It does not open GPIO,
serial, UDP, motor, relay, or track-power transports.
